# 設計原則

1. 想定視聴者は従来どおりAI・ソフトウェア技術に関心のあるエンジニア。前提知識は
   高校生レベルまでとし、専門用語は使う場面かその直前で平易に導入する。
2. 8〜14場面にし、セリフ総文字数の設計値を3,600〜4,200字に置く。
3. 基本線は `困りごと → 中心の問い → 一文の答え → 全体図 → 代表例 → 原理 →
   一次資料・実測 → 失敗例・限界 → 判断 → 冒頭の回収`。資料に合わない段は省いてよいが、
   `transition_reason` で前の場面から進む理由を必ず説明する。
4. 各場面は1論点、1つの理解目標に絞る。同じ結論の言い直しで場面数を増やさない。
5. 透には毎場面、予想、誤解、反例、用語質問、新しい例への適用のいずれか、または
   内容上必要な別の仕事を持たせる。澪の説明を「つまり〜のですね」と確認するだけの
   役にしない。
6. 澪と透の世界観イベントは2〜3場面に1回を目安にする。からかいは全体で1〜3回とし、
   同じ「透の早合点を澪がからかう」型を複数回使わない。褒め→照れ、安心させる、
   透の観察で澪が説明を組み直す、終盤で澪が具体的な成長を認める、など内容に結びつく
   異なる型へ分散する。感情の変化を半数以上の場面へ自然に置く。
7. 図解優先。一次資料の図が直接支える場合は`figure`、関係や手順は意味に合う
   `diagram`、視覚化できない残余だけを`bullets`や`quote`にする。
8. `claim_ids` は資料理解に存在するIDだけを使う。資料の限界を越える場面を作らない。
9. URL、アクセストークン、メールアドレスはJSONへ出力しない。
