提案の骨子: 採点を「Layer 1 機械指標（コードで毎回自動計測）」「Layer 2 LLM審査 7軸100点（アンカー付き絶対採点）」「Layer 3 視聴審査（音声・映像）」「Layer 4 視聴者実測（理解テスト・A/B）」の4層に分ける。指摘の3点（用語が難しい・世界観の掛け合いが少ない・感情が乏しい）は、現行の検証コードとCodex審査のどちらにも対応する軸が存在しないことを確認した。調査した評価研究（PodEval・PodAgent）にも感情・掛け合いの専用軸はなく[2][3]、ここは自作になる。

ベースライン実測: 保存済み台本「AIは1939年の数学難問を解いた？」を本基準で採点すると 52/100（詳細は§6）。機械指標も8項目中6項目が目標未達で、指摘された弱点が数値でそのまま現れる。

1. 事例調査から何を採り、何を自作するか

レポート[1]で参照されている評価研究2本とOSS 5実装について、一次資料（論文本文・リポジトリの実プロンプト）を読み直した。採点基準に取り込める要素は次の通り。

出どころ採用する設計出典
PodEval（評価フレームワーク研究） ①台本(text)・音声(speech)・番組全体(audio)を別々に採点する3層分離。②各層で客観指標（自動計算）と主観評価（人手）を併走させる分担。③対話自然さのMUSHRA 5段階の言語アンカー（「完全に機械的」〜「実際の自然な会話に聞こえる」）。④質問紙の「表現の好み」「引き込み」「続きを聞きたいか」「人間らしさ」。⑤重要知見: 1文ずつのTTS合成は対話自然さを大きく損なう（1文合成のPodAgentが最下位、対話まるごと合成のMoonCast等が上位、NotebookLMは実在ポッドキャストに次ぐ2位）。 [2]
PodAgent（ACL Findings 2025） ①LLM審査の6軸: 一貫性・引き込み・多様性・情報性・話者ごとの視点の差別化・総合。②審査手順の原則: 先に分析を書かせてから採点させる、比較時はA/Bを入れ替えて2回評価し平均（位置バイアス対策）。③役割分担生成が一括生成に勝る定量根拠（単一エージェント化で情報密度が約17%低下、意味的多様性がほぼ半減）。ただし採点は2本比較の相対方式（−3〜+3）なので、単発動画には軸だけ借りて絶対尺度へ読み替える。 [3]
OSS 5実装の生成プロンプト プロンプトが「良い台本の条件」として明文化している基準を採点側へ移す。①強いhookで開始→徐々に複雑化→息継ぎ→締めで自然に要点回収（open-notebooklm）。②モノローグ禁止・話者は互いに反応する（SurfSense・podcast-creator）。③言い淀み・割り込み・相槌を入れるが乱用に上限（podcast-llm「sparingly」、NotebookLlamaは話者別に許可表現を限定）。④初学者役＋比喩・逸話・実例で平易化（NotebookLlama「anecdotes and analogies sprinkled throughout」）。⑤根拠のない主張の禁止、語数の目標配分。 [4] [5] [6] [7] [8]
自作が必要な空白 感情表現の質、キャラクター同士の関係性（いちゃつき）、掛け合いの深さを直接測る軸はどの事例にも存在しない（PodEvalは「表現の好み」という選好質問のみ、PodAgentは視点差別化のみで、両論文とも掛け合い専用指標が無いことを確認）。レポートの「審査は模倣でなく新規設計が必要」という結論[1]と一致。§4のR5・R6が自作部分。 [2] [3]

2. 採点システム全体像 — 4層

PodEvalの3層分離に、レポートの検証指標[1]（理解テスト・視聴意向）を4層目として足した構成。安い層から順に毎回回し、高い層は節目だけ回す。

LAYER 1 · 毎生成

機械指標（8項目）

コードで決定論的に計測。総文字数・発話バランス・世界観イベント数・感情マーカーなど。script_gen._validateの拡張として実装可能。

LAYER 2 · 毎生成

LLM審査 7軸 100点

アンカー付き絶対採点。根拠ゲート＋平易さ25・世界観20・感情15・掛け合い15・順番15・引き込み10。既存Codex審査の後段に追加。

LAYER 3 · 完成動画

視聴審査（音声・映像）

人が動画を見て採点。対話自然さ（MUSHRA式5段階）、声と感情の一致、図解の適切さ、字幕・同期。

LAYER 4 · 節目のみ

視聴者実測

理解テスト5問（新旧+10pt目標）、話者名を隠したA/B視聴意向70%。方式変更の採否判定に使う。

運用原則（PodAgentの審査原則を移植[3]）: LLM審査は軸ごとに「まず根拠となる分析を書く→その後に採点する」形式にする。新旧方式の比較をするときだけ、PodAgent/PodEvalと同じ2本比較（A/B入れ替え2回の平均）を使う。単発動画の合否は絶対アンカー方式で判定する。

4. Layer 2 — LLM審査 7軸（アンカー付き絶対採点・100点）

各軸1〜5点で採点し、重み付けして100点に換算する。配点は指摘の3点（平易さ・世界観・感情）を厚くした: 平易さ25・世界観20・感情15・掛け合い15・教える順番15・引き込み10。R1根拠は点数化せずゲート（不合格なら公開不可）。

R1 根拠・正確性

ゲート（配点なし）

定義: すべての技術的断定が元資料に遡れる。推測はセリフ内で推測と分かる。危険なコマンド・数値の捏造なし。現行Codex審査[9]の役割をゲートとして明文化するもの。

合格元資料にない断定が0件。OSS共通の「根拠なき主張の禁止」[4][5]と同じ基準。
不合格事実誤り・元資料にない断定が1件でもあれば、他の点数に関わらず公開不可。該当シーンのみ再生成。

R2 平易さ（高校生基準）

25点指摘①対応

定義: 高校生レベルの前提知識で全シーンを追えるか。専門用語は初出時に日常語の言い換え・比喩・実例のいずれかで導入する。想定視聴者（エンジニア）は変えず、要求する前提知識の水準を高校生レベルまで下げるという方針。中心概念には比喩か実例を最低1つ付ける（NotebookLlamaの「逸話と比喩を全体に散りばめる」[7]、open-notebooklmの「複雑な話題を一般聴衆に届く形に」[4]）。

5全用語が初出時に平易に導入され、中心概念に比喩・実例がある。専門用語を知らなくても各シーンの結論が理解できる。
3大半は平易だが、未説明の専門用語が1〜2語残る。または説明はあるが抽象的で、比喩・実例が無い。
1未説明の専門用語が連発され、それを前提に話が進む。（例: 現行台本の「Jacobian予想」——何の分野の何についての予想か一度も説明されない[12]）

連動する機械指標: M7未定義語。審査時にLLMへ「この台本を高校1年生が読んで、各シーンの結論を自分の言葉で説明できるか」を分析させてから採点する。

R3 教える順番・理解の前進

15点

定義: 各シーンが固有の問いを持ち、前のシーンまでの理解を前提に一歩ずつ進む。仕様の説明順（困りごと→問い→一文の答え→全体図→…→回収[10]）に沿い、重複と飛躍が無い。PodEvalのcoherence軸[2]とレポートの「学習状態」設計[1]に対応。

5全シーンで「このシーンで新たに分かること」が特定でき、前提が未説明のまま使われる箇所が無い。
3骨格は守られているが、同じ理解目標の重複、または一段飛ばしが1〜2箇所ある。
1資料の順番をなぞるだけで、視聴者の理解が積み上がる設計になっていない。

R4 掛け合いの質

15点

定義: 透が理解を前進させる仕事（質問する・予想する・誤解する・反例を出す・別の例に当てはめる）をし、澪がその反応を受けて説明を一段戻す・例を変える。説明文の交互読み上げやモノローグにならない（SurfSense「互いに反応させる」[5]）。PodAgentの「話者ごとの視点の差別化」軸[3]を2人用に読み替えたもの。

5シーンの過半で透の認知イベントが会話を動かし、少なくとも1回は透の疑問で澪が説明を組み直す。
3質問はあるが、透の返答の多くが澪の説明の言い換え確認。会話が無くても説明が成立してしまう。
1透は相槌と復唱のみ。掛け合いを外しても情報が変わらない。

連動する機械指標: M2発話バランス・M3言い換え確認率。

R5 キャラクター・世界観

20点指摘②対応

定義: 透の無邪気な憧れと澪の大人の余裕が、技術の話の流れの中で自然に現れるか。いちゃつき（からかい→動揺、褒め→照れ、名前呼び、距離感の演出）が2〜3シーンに1回あり、毎回ちがう形で起きる。既存事例に対応軸が無い自作軸（§1）。禁止側は現行プロンプト[10]のまま: 説明と無関係な恋愛会話・毎回同じ口癖・過剰な色気は減点。

5甘酸っぱいやり取りが2〜3シーンに1回、説明内容と絡んで起きる（例: 透の的確な指摘を澪が褒めて透が照れる、澪のからかいが透の誤解の指摘を兼ねる）。表現が毎回異なり、視聴者が2人の関係の進展を感じられる。
3イベント数は足りるが定型の繰り返し（毎回同じ照れ方・同じ台詞回し）、または説明の流れから浮いている。
1役割どおりの業務的な会話のみで、2人の関係性が台本から消えている。

連動する機械指標: M4世界観イベント数（下限チェック）・M8定型反復。数はM4で保証し、質はこの軸で採点する——現行台本はM4合格でも、照れ3回がすべて「そ、…」＋「少し照れますが」の同型で、ここが3点止まりになる。

R6 感情表現

15点指摘③対応

定義: 驚き・喜び・困惑・安心が言葉そのものに出ているか（感嘆・間投詞・言い淀み・声に出る笑い）。感情の山が各章に1つ以上あり、立ち上がりと戻りがあって、ポーズ（表情）と語調が一致する。話者別の使い分けを守る: 透は言い淀み・感嘆を厚く、澪は落ち着きを基調にpraise/teaseで感情の山を作る（NotebookLlamaの話者別許可表現[7]と感情TTS調査のdelivery設計[13]に整合）。乱用は禁止（podcast-llm「sparingly」[6]）。

5各章に感情の山があり、ポーズと言葉が一致（flusteredのセリフは実際に慌てた言葉遣い）。感嘆・言い淀みは要所のみで、説明部は落ち着いている。
3感情語はあるが平板・定型（照れの表現が毎回同じ等）、またはポーズだけ変わって言葉が説明調のまま。
1全編が説明調で感情の起伏が無い。（現行台本: 全47セリフに感嘆符0[12]）

連動する機械指標: M5感情マーカー・M6ポーズ多様性。音声側の演技（VOICEVOXスタイル切替）はLayer 3で別途採点し、ここでは台本の言葉だけを見る。

R7 引き込み

10点

定義: 冒頭のhook（透の困りごとが具体的で他人事でない）、緩急と息継ぎ、締めでの自然な要点回収と前向きな終わり方。open-notebooklmのペーシング基準[4]（強いhook→徐々に複雑化→息継ぎ→高揚した締め）と、PodEvalの引き込み・聴取継続意向[2]に対応。

5冒頭30秒で「自分も引っかかりそうだ」と思わせ、難所の後に息継ぎがあり、締めが冒頭を回収して次も見たくなる。
3hookはあるが、中盤が単調、または締めが要点の列挙で終わる。
1定義や資料紹介の読み上げから始まり、平坦なまま唐突に終わる。

5. Layer 3・Layer 4 — 完成動画の審査と視聴者実測

Layer 3: 視聴審査（完成動画を人が見る）

項目方法根拠
対話の自然さPodEvalのMUSHRA言語アンカーを5段階に翻訳して使う: 1=完全に機械的で会話に聞こえない / 2=不自然さが目立ち機械的な調子が多い / 3=ある程度自然だがリハーサル的で繋ぎがぎこちない / 4=概ね自然で実際の会話に近い / 5=人同士の自然な会話に聞こえる[2]
声と感情の一致感情の山のセリフを抜き出し、声の演技がポーズ・内容と合っているかをセリフ単位でpass/fail判定（PodAgentの音声-役割マッチングの合格率方式[3]を流用）。VOICEVOXスタイル演出[13]導入後の効果測定を兼ねる[3] [13]
図解の適切さ図型と意味の一致（対立=matrix、因果=flow…）、一次資料図の優先、図とセリフの同期。既存の図解優先ポリシーのチェックリスト化[9]
字幕・読み・同期読み間違い、字幕の改行・見切れ、口パクのずれの有無[9]
既知の天井: 現行は1セリフずつVOICEVOX合成しており、PodEvalはまさにこの1文単位合成が対話自然さを損なうことを示した[2]。台本採点が満点でも対話自然さには構造的な上限がある。まず台本層を改善し、音声はVOICEVOXスタイル演出（Phase 1）→AivisSpeech（Phase 2）[13]の順で別実験として測る。

Layer 4: 視聴者実測（方式変更の採否判定・節目のみ)

  • 理解テスト: 動画内容の確認5問。新方式が旧方式より正答率+10pt以上（レポートの検証指標[1]）。
  • 視聴意向A/B: 話者名を隠した2本比較で、70%以上が新方式を「続きを見たい」と選ぶ[1]。比較時はPodAgentの手順どおりA/Bを入れ替えて2回聞かせる[3]。

6. ワーク例 — 現行台本のベースライン採点

保存済み台本「AIは1939年の数学難問を解いた？見出しを検証する」[12]（10シーン47セリフ）を本基準で採点した。Layer 1は実測値、Layer 2は提案者（Claude）による手動採点例で、LLM審査を組んだら置き換える。

軸配点採点得点根拠（実測）
R1 根拠・正確性ゲート合格（参考）—記事の主張と数学的事実を区別する慎重な内容。ただし元資料との突合は未実施のため参考判定
R2 平易さ252/510主題の「Jacobian予想」が何の予想か全編で一度も説明されない。「証拠の層」「断定の強さ」も抽象的。比喩・実例0件
R5 世界観203/512イベント数は4回で下限クリア。しかし照れ3回がすべて同型（「そ、…」×2、「少し照れますが」×2）で、tease 1回のみ。関係の進展が見えない
R6 感情表現152/56感嘆符0、間投詞を含むセリフ3つのみ。透が「驚く・喜ぶ」場面でも言葉は説明調のまま
R4 掛け合い152/56透の実質的な質問は3/15。言い換え確認が約半分（7/15）。透26発話中質問3という前回台本[1]と同じ構図
R3 教える順番154/512困りごと→問い→一文の答え→全体図→原理→限界→回収の骨格は良好。シーン6と2に部分的な重複

7. 運用への組み込み

  1. 今すぐ（実装済み）: Layer 1はuv run python scripts/score_lecture.py <job_dir>で計測し、--emit-judge-promptでLayer 2審査プロンプト（scripts/prompts/lecture_score_judge.md）を生成できる。Claude Codeでは.claude/skills/lecture-scoringスキルが両層を実行する。既存台本と次の2〜3本を採点し、レポート推奨(1)の「変更前の表」[1]としてベースラインを残す（M7のみLLM審査、M3は「のですね」型の代理指標で自動計測）。
  2. 台本工程の改善後（レポートの週6〜7に対応）: Layer 2を「教え方レビュー」としてパイプラインに組む。既存Codex審査（技術）とは別呼び出しにし、軸ごとに分析→採点→不合格シーンだけ再生成。誤検出が多ければ自動書き直しは止めて採点表示に留める（レポートの撤退条件[1]）。
  3. 仕様の同期（実装時に必須）: R2を採用する場合、現行プロンプトの「想定視聴者はエンジニア」[10]に「前提知識は高校生レベルまで、専門用語は必ず導入する」を追記し、M1の総文字数判定を_validateへ追加する。仕様とコードの同時更新（CLAUDE.mdのSpec-Code Consistency）。
  4. 音声・映像（Layer 3）: VOICEVOXスタイル演出[13]を入れた時点から「声と感情の一致」を測り始める。それまでは台本層の改善に集中する（原因の切り分け[1]）。

8. 限界と未決事項（誠実な開示）

  • 暫定目標値: M1〜M8の数値とR軸の配点は丸めた暫定値。3〜5本の実測とユーザーの体感評価で調整する。
  • 未定義語の自動化: 用語抽出は完全には機械化できず、LLM抽出＋コード照合のハイブリッドになる。誤検出率は運用しながら確認。
  • 世界観の「質」: M4は下限の保証のみで、いちゃつきの質はLLM審査（R5）と最終的には人の目に依存する。R5のアンカーが安定するまで、ユーザーの体感とLLM採点のずれを数本分突き合わせる工程が必要。
  • 採点の再現性: LLM審査は同一台本でも点がぶれうる。PodAgent方式（分析先行・複数回平均)で緩和するが、ゲート判定（R1）以外は傾向把握用と割り切る。
  • 相対比較との使い分け: PodEval・PodAgentの採点は2本比較の相対方式であり、本提案の絶対アンカーは独自の読み替え。方式変更の採否はLayer 4の相対比較で最終判定する。
