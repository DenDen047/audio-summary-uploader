# 改善計画：自分用優先・公開はおまけ（2026-06-28）

本書は audio-summary-uploader の今後の改善計画。市場調査（`docs/market-research-2026-06.md` v2）と既存コンテンツの型分析（同 §1.6）、およびユーザーの方針決定に基づく。

## 0. 方針（確定事項）

- **目的は「まず自分用」**。収益化は難しい前提で主目的にしない（市場調査の収益化最適化＝原案エッセイ型への全面転換は**採用見送り・参考保持**）。
- **基本は単一ソース→音声**を維持。**複数ソースを1音声にまとめる**構成も追加。
- **ニッチ＝自分が気になるニュース/論文**（自分用まとめ）。
- **1チャンネル＋カテゴリ別プレイリスト**で運用（チャンネル分割はしない）。
- 公開は続けるため **身バレ防止・個人情報非露出は必須要件**。
- **LLM処理は基本 NotebookLM のチャット（`ask`）で行う**（追加コストゼロ）。`notebooklm-py v0.5.0` に `client.chat.ask(notebook_id, question)` があることを確認済み。補助LLM（Gemini）は**フォールバック**に限定。
- **追加コストはゼロ〜極小**を維持。
- **シンプルに始める**：P0 から最小構成で着手し、段階的に拡張。

## 3. 機能仕様（優先度順）

各項目: **目的 / 設計 / 主な変更ファイル / 受け入れ条件**。

### P0 — 最小スタート

#### ⓪（基盤）NotebookLMBackend に `ask()` を追加
- **目的**: ①②③④ の土台。NotebookLM のチャットを抽象インターフェース経由で使えるようにする。
- **設計**:
  - `NotebookLMBackend` に `async def ask(notebook_id, question, source_ids=None) -> str` を追加。
  - notebooklm-py 実装: `client.chat.ask(notebook_id, question)` を呼び `result.answer` を返す（確認済みAPI）。Playwright実装は将来対応（当面 notebooklm-py）。
  - **呼び出しタイミング**: collect フェーズで音声生成が完了し、**ノートブック削除の直前**にまとめて chat 抽出（①②③のためのQ&A）を実行する（ノートブックが存在する間に取得）。submit 時に行う案もあるが submit を軽く保つため collect 推奨。
- **変更ファイル**: `notebooklm.py`（抽象に`ask`追加）、`notebooklm_py_backend.py`（実装）、`pipeline.py`（collectで呼び出し）。
- **受け入れ条件**: 任意のノートブックに日本語で問い合わせ、回答テキストが返る。

#### ① Sparkメール出典抽出（NotebookLM chat）＋ 生リンク秘匿  ★最優先
- **目的**: Sparkメール共有リンクのメタデータ取得失敗を解消し、**個人メール由来の生URLを公開面に出さない**。同時に**自分は後から出典を辿れる**ようにする。
- **設計**:
  - ノートブックに追加済みのソース（Sparkメール本文）に対し chat で問い合わせ：
    `「このメール（ソース）の『件名・送信者の表示名・送信ドメイン・送信日(YYYY-MM-DD)』だけをJSONで返してください。分からない項目はnull。」`
    → パースして出典に使う。出典表記 `出典: {送信者名}（{ドメイン}）- {日付}`。
  - **Spark共有URL は state.json にそのまま保持（自分用の参照）**。ただし**タイトル・概要欄・サムネなど公開面には一切出さない**（§P1-⑤ のサニタイザを最後の砦に）。
  - 抽出失敗時フォールバック: 出典は「(出典情報は取得できませんでした)」等にし、**生URLは絶対に出さない**。
- **変更ファイル**: `metadata.py`（spark検出→chat抽出に委譲）、`pipeline.py`、`youtube.py`（概要欄出典）、状態管理（公開用フィールドと private URL を分離）。
- **受け入れ条件**: Sparkメール由来動画の公開面に**生の共有URL/個人メールアドレスが出ない**。出典が「送信元名＋日付」で表示される。state.json には元URLが残る。
- **注**: IMAP直接読み取り案は不要に（NotebookLM chatで完結）。Gmail App Password等のセットアップも不要。

#### ② 日本語タイトル自動生成（NotebookLM chat）
- **目的**: 英語/ファイル名/URLのままのタイトルを、**自分が後から探せる日本語タイトル**に。
- **設計**:
  - chat で問い合わせ：`「この内容にふさわしい日本語のYouTubeタイトルを1つだけ。全角35字以内、内容に忠実、煽りすぎない、記号で囲わない。」`
  - 失敗/空時は元タイトルにフォールバック。先頭 `🎧` は撤去 or 末尾へ。
- **変更ファイル**: `pipeline.py`（collectでchat）、`youtube.py`（生成タイトル使用）。
- **受け入れ条件**: arXiv/PDF/YouTube/Spark 各ソースで日本語の通るタイトルが付く。chat不通でも元タイトルで継続。

#### ③ カテゴリ自動判定＋プレイリスト自動振り分け
- **目的**: ジャンル混在を解消し、自分の蓄積をプレイリストで整理。
- **設計**: §2 のルールベース第一・NotebookLM chat補完でカテゴリ決定 → カテゴリ→`playlist_id`（`settings.yaml`）→ `playlistItems.insert`。単一 `playlist_id` を `playlists: {category: id}` へ拡張（後方互換）。
- **変更ファイル**: 新規 `category.py`、`config.py`、`youtube.py`、`pipeline.py`。
- **受け入れ条件**: 各動画が想定カテゴリのプレイリストに入る。未分類は既定へ。

### P1 — 品質

#### ④ サムネは“常にAI画像生成”（OGP使用は廃止）  ★気合い枠 — 検証済
- **目的**: ソースに関わらず、毎回キャッチーなサムネをAIで生成（OGP流用＝著作権リスクも回避）。
- **方式（検証で確定）**: **Nano Banana(gemini-webapi)で「文字入りサムネ」を丸ごと生成する方式(A)を主**。検証で、長め・専門的な日本語見出し（例「なぜ蒸留で拡散モデルは爆速化したのか？【論文解説】」）も**全文字正確＋自然な改行＋ゴールド縁取りのプロ級**に一発生成できた（＝Pillow折返しの不自然さ問題を回避）。
- **設計**:
  1. **見出し生成**: NotebookLM chat（②）でタイトル生成→`[N]`除去。
  2. **サムネ生成(A・主)**: gemini-webapi に「16:9・**固定スタイル仕様**（カテゴリ別の配色/モチーフ/ゴールド縁取り等でブランド統一）＋見出し文字をそのまま描画」を指示→ 2752×1536生成 → 1280×720へ整形。
  3. **フォールバック(B)**: AIが文字を崩す/文字なし背景にしたい場合は、文字なし背景＋**Pillowで日本語後乗せ**（NotoSansJP-Bold 同梱・描画は検証OK。ただし**既存 `_wrap_text` は禁則処理なし→要改善**）。
  - OGP画像の使用は廃止。
- **変更ファイル**: 新規 `image_gen.py`（gemini-webapi ラッパ＋cookie源=`storage_state.json`）、`thumbnail.py`（整形＋Pillowフォールバック＋禁則処理改善）、`config.py`（カテゴリ別スタイル）。
- **受け入れ条件**: 全ソースで文字入りのオリジナルサムネが出る。A が崩れた時は B で確実化。
- **留意**: A は生成ごとに体裁が揺れる→**プロンプトに固定スタイル仕様を必ず入れてブランド統一**。希少文字での誤字や厳密一致が要る場合は B。

#### ⑤ 概要欄整形＋個人情報の自動除去
- **目的**: 出典を整え、**個人情報（メアド/個人URL/Spark生リンク）が絶対に出ない**ように。
- **設計**: 概要欄テンプレ（冒頭2-3行＋出典＋チャプター＋ハッシュタグ3〜5）。出力直前に**サニタイザ**でメールアドレス正規表現・`sparkmailapp.com/web-share` 等を検出除去（最後の砦）。
- **変更ファイル**: `youtube.py`（説明テンプレ＋サニタイズ）。
- **受け入れ条件**: いかなるソースでも概要欄に個人情報が残らない（自動テストで担保）。

#### ⑥ 音声/動画メタデータの個人情報除去
- **目的**: mp3/mp4 のメタデータにローカルパス/個人情報を残さない。
- **設計**: 生成後に mutagen 等でメタデータをクリア/中立値に上書き。
- **変更ファイル**: `video.py` or 新規 `sanitize.py`、`pipeline.py`。
- **受け入れ条件**: 出力 mp4 のメタデータに個人名/ローカルパス/メアドが無い。

### P2 — 構成拡張

#### ⑦ 複数ソース→1音声
- **目的**: 「たまに複数ソースをまとめて1本に」（例: 今週のAIニュースまとめ）。
- **設計**: `urls.yaml` で複数URLを1エントリに束ねる（後方互換）。
  ```yaml
  - url: https://arxiv.org/abs/2511.15059        # 単一（現行）
  - title: 今週のAIニュースまとめ                  # 複数（任意title、無ければchat生成）
    urls:
      - https://app.sparkmailapp.com/...
      - https://www.theinformation.com/...
    prompt: news_summary
  ```
  `UrlEntry` を「1つ以上のソース＋共通設定」に内部正規化。NotebookLM は1ノートブックに複数 `add_source`。slug はグループ単位ハッシュ。
- **変更ファイル**: `url_parser.py`、`pipeline.py`、`metadata.py`、状態管理。
- **受け入れ条件**: 複数URLを束ねた1エントリから1本生成、概要欄に全出典。単一URLの既存挙動は不変。

## 6. 要確認（次に決めること）— D3: サムネ画像生成エンジン

「気合いを入れた画像生成」を全動画で回す手段。3案を比較（2026-06調査）:

| 案 | コスト | 画質 | 認証/準備 | リスク |
|---|---|---|---|---|
| **(A) gemini-webapi**（Nano Banana・Gemini Web版/サブスク） | **¥0（サブスク内）** | 高（Nano Banana） | cookie `__Secure-1PSID`/`__Secure-1PSIDTS`、または `browser-cookie3` でChromeから自動取得 | 非公式・ToSグレー・cookie切れ/仕様変更で停止（notebooklm-py と同種） |
| **(B) ローカル FLUX.1 schnell**（mflux） | ¥0（電気のみ） | 中〜高 | モデルDL数GB・M5/32GBで快適・オフライン | 公式OSS・安定（ToS問題なし） |
| (C) 公式 Gemini API（Imagen） | 有料（画像は無料枠なし） | 高 | APIキー | 安定だが課金 |

- **NotebookLM 自体の画像生成**は Nano Banana Pro 統合済だが **インフォグラフィック/スライド/Video Overview挿絵**に限定（`generate_infographic`=PNG, 3向き/3詳細度）。**自由なサムネ生成には不向き**（freeformプロンプト不可）→ サムネは A/B から選ぶ。
- **決定: (A) gemini-webapi（Nano Banana）を採用**（`image_gen.py` で抽象化、(B)は将来フォールバック）。
- **検証済み（2026-06-28）**: NotebookLM と同一アカウントで gemini-webapi init→生成成功。出力 **2752×1536（16:9）高解像度** → 1280×720へ整形。
- **文字入れ検証（2026-06-28）**: Nano Banana は**日本語見出しを正確描画＋自然改行**できた（長め・専門用語・【】・？も崩れず、ゴールド縁取りのプロ級）。→ **方式A＝文字入りサムネをAIが丸ごと生成**を主に。Pillow後乗せ(B)も NotoSansJP-Bold で描画OK・ただし折返しに**禁則処理が必要**（既存 `_wrap_text` は素朴）。B はフォールバック。
- **cookie源**: NotebookLM の `~/.notebooklm/profiles/default/storage_state.json` に `__Secure-1PSID`/`__Secure-1PSIDTS`（.google.com）が入っており、これを読めば**Chromeログイン不要・同一アカウント**で動く（PSIDTSは自動リフレッシュ）。
- **留意**: アカウントはユーザー選択により NotebookLM と同じ（会社Workspace）。非公式API利用＝会社ポリシー次第（チャンネルには露出しない）。画像生成可否は地域/アカウント依存・18歳未満不可。
- **(B) ローカルFLUX / Modal**: 外出先利用も視野に将来 Modal（サーバーレスGPU）で動かす案。現状は後回し（Defer）。
- **実装メモ**: `gemini-webapi` を依存に追加。プロンプトは NotebookLM chat で「内容→英語の画像プロンプト」を生成→gemini-webapiで生成→Pillow合成。

## 7. リスク・前提

- **NotebookLM chat の信頼性**: 抽出/タイトルはハルシネーションし得る → 構造化プロンプト＋検証＋フォールバック必須。日付など元ソースに無い情報は null 扱い（捏造させない）。
- **NotebookLM依存**: 非公式手段のため停止リスク（SPEC §8）。chat APIも同様。停止時は Gemini フォールバックへ。
- **著作権/規約**: 自分用＋公開だが収益化しない前提。YouTube動画要約等のグレーは許容（ユーザー確認済み）。出典明示・要点中心を維持。
- **身バレ防止**: ①・⑤・⑥・⑧ が該当。個人情報除去は**自動テストで担保**。
- **音声長 `short`**: 日本語で実際に効くか実機確認（research §6 未確認）。
